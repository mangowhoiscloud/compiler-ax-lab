승인할 내용과 남은 결정

검산과 설계 개정을 마쳤으며 실제 실행은 대기 중입니다. 이 페이지의 시간은 계산 예시입니다. 원격 자원 준비, 키 생성, 모델 호출, 컴파일러 실행은 진행하지 않았습니다. 실행 예산과 접근 권한을 확정하기 전에는 E0/E1을 시작하지 않습니다.

승인 제안: 공개 Rust 유지보수 과제 하나로 시작하고, 일반 Codex와 변경·검증 절차를 명시한 Codex를 비교합니다. 에이전트가 만든 코드의 양보다 정확한 변경을 검토하는 데 든 총 사람 작업시간을 우선 봅니다. B는 절차를 묶은 개입이므로 첫 비교만으로 어느 구성 요소가 효과를 냈는지는 구분할 수 없습니다.

품질 기준: 기존 컨벤션을 지키고 실제 판정 능력을 확인합니다

Furiosa 9b9cf0f / 0.8.1, Dioxus ada3b67의 공개 코드와 Dioxus 보존 전사를 대조했습니다. 수용 기준은 A/B 공통입니다. B에만 절차 안내를 추가하며 검사 문턱·보호 정답·도구 차이를 효과로 세지 않습니다. 컨벤션·품질 계약 정본과 원문 대장에 상세 조건을 남겼습니다.

코드 컨벤션: 대상 crate·호출자·기존 테스트를 읽고 기존 helper·이름·오류 처리와 120자 포맷을 유지합니다. 첫 수정 범위는 테스트·필요 helper·설명입니다. kernel·runtime·dependency·unsafe/FFI 변경이 필요하면 재합의합니다. blanket allow, 검사 삭제, ignore 추가, assertion·허용 오차 완화로 통과시키지 않습니다.

단계확인할 것통과가 뜻하지 않는 것

실행 순서: 공개 Q1–Q3에서 실패하면 허용된 재제출·예산 안에서 수정합니다. snapshot 고정 뒤 Q4를 한 번 시행합니다. 보호 실패 뒤 수정은 새 실험입니다. lint 예외·적용하지 않을 검사는 시작 전에 담당자가 근거와 함께 승인하며 사후 제외로 성공률을 높이지 않습니다.

재사용할 명령: make fmt, make check, make clippy, cargo machete, make test입니다. fmt는 check-only, clippy는 -D warnings, test는 release입니다. 문서 build와 예제 실행을 분리합니다. Furiosa의 clippy-npu는 별도 target이며 Dioxus의 --all-features를 그대로 적용하지 않습니다.

실재하는 smoke 후보 명령은 cargo test -p furiosa-opt-examples --release --test binary_add_tests -- --list입니다. 이름을 확인한 뒤 마지막 인자를 -- --exact test_binary_add_2048로 바꿔 실행합니다. 목록 조회도 빌드를 유발할 수 있습니다. double_buffering_tests.rs는 만들 파일의 제안명이며 아직 실행한 테스트가 아닙니다.

Dioxus에서 확인한 경고: 축소된 퍼징 실패는 strict 회귀 테스트로 재생하지만 전체 corpus의 coverage 재생은 비교 결과를 의도적으로 무시합니다. 명령 성공만 보고 정확성 통과로 기록하면 안 됩니다. 첫 파일럿은 고정 경계 입력으로 시작하고 후속 탐색에서 발견한 실패를 축소·검토해 회귀 검사에 남깁니다. 무제한 퍼징·새 CI 서비스는 추가하지 않았습니다.

이 표는 검사 설계입니다. Rust 검사·원격 CI는 아직 실행하지 않았습니다. 기존 컨벤션을 따르되 평가 기준의 변경 권한은 후보에게 주지 않습니다.

PR·병합: 검사한 revision과 사람이 받아들인 변경을 연결합니다

병합 절차와 실제 PR 템플릿을 분리 작업공간에 추가했습니다. 작은 branch → 로컬 검사 → Draft PR → 현재 head/base 통합 검사 → 사람 검토 → 병합 → main 재검사 순서입니다. 실패하면 수정 또는 revert PR로 처리하며 릴리스는 별도 승인입니다.

lab 문서 CI는 lab-docs 결과를 lab-ci가 항상 집계하고 정확한 success만 허용합니다. 이 CI는 문서·링크·공개 파일·산술 검사이며 Q0–Q5의 실제 Rust/장치 검사를 대신하지 않습니다. CODEOWNERS와 템플릿만으로 독립 리뷰가 강제되는 것도 아닙니다. 서버 보호 규칙은 실제 GitHub 설정으로 따로 확인합니다.

이 저장소는 운영자용입니다. A/B 후보는 별도 clean checkout에서 실행하며 전체 설계 컨텍스트를 읽지 않습니다. 공개된 오류 예시는 공개 개발용으로만 쓰고 최종 독립 확인에는 다른 비공개 입력·판정을 사용합니다. lab 공개와 Furiosa upstream 제출·병합은 다른 권한입니다.

첫 과제는 무엇을 고치고, 무엇으로 확인할까?

furiosa-opt 0.8.1 / 9b9cf0fdc78df00cdc430eae725a5ad9084a735e의 double-buffering 예제에는 rolled, software-pipelined, unrolled 구현이 있습니다. 첫 과제로 제안하는 일은 세 구현의 그룹별 출력과 경계 처리를 확인하는 회귀 검사 보강입니다. 제품 버그를 발견한 상태는 아닙니다.

별도 기대값 계산 out[t,g,o] = sum_r activation[t,r] * weight[g,o,r]과 비교하도록 설계합니다. 처음에는 반올림 해석이 명확한 작은 입력과 그룹별로 다른 값을 씁니다. 첫·마지막 그룹과 잘못된 그룹 짝을 구별하도록 하되, 정확한 입력·허용 오차·범위는 실행 전에 고정합니다. 테스트를 추가하는 과제이므로 테스트 파일의 존재가 아니라, 보호된 정상·의도 오류 코드에 그 테스트를 적용했을 때 제대로 구별하는지 확인합니다.

의도적으로 마지막 그룹을 누락한 코드는 검사기의 준비를 확인하기 위한 대조군입니다. 실제 Furiosa 결함으로 보고하지 않습니다. 준비 과정의 답·로그와 보호 입력은 A/B 후보 세션에 전달하지 않으며, 공개 요구와 추가 설명은 양쪽에 동일하게 제공합니다.

검산 결과: 대기를 없앤 기준선과 비교합니다

같은 후보 3개, 공통 준비 15분, 후보당 생성 10분·검사 20분, 최종 검토 15분을 가정합니다. 앞서 제시한 120분은 생성 전체가 끝날 때까지 검사를 기다리는 시간입니다. 준비 즉시 실행하는 같은 정책끼리 비교하면 100분 → 80분입니다. 병렬 쪽의 추가 비용이 5분이면 85분으로, 약 1.18배입니다. 이 조건에서 CPU 슬롯이 2개이면 LLM 슬롯 1개와 3개의 결과는 같습니다.

단계 대기 모델은 T = s + ceil(k/pL)·g + ceil(k/pE)·e + f + h입니다. s는 준비, f는 최종 통합·검토, k는 고정 후보 수, pL/pE는 모델/검사 슬롯, g/e는 후보당 작업시간, h는 식에 들어 있지 않은 추가 조정 비용입니다. 실제 계획에서는 작업별로 검사 시작 = max(후보 준비 시각, CPU 슬롯 가용 시각), 검사 종료 = 시작 + 해당 조건에서 측정한 검사시간을 기록합니다. 이 시각에 포함된 큐 대기를 h에 다시 더하지 않습니다.

후보별 검토를 추가하면 판단 시작은 max(실행 종료, 검토 종료)입니다. 생성과 검토가 같은 LLM 용량을 쓰면 서로 경쟁합니다. 위 표에는 추가 검토 호출이 없으므로 ToC를 더한 시간으로 해석하지 않습니다. 사람의 시간은 동시 작업 수로 나누지 않고 담당자별 person-minutes를 합합니다.

E0의 검사 전용 예시는 T1 = 3e1, T2 = 2e2 + h입니다. e1/e2는 슬롯 1/2 조건에서 작업당 검사시간이며, 병렬화는 2e2 + h < 3e1일 때 유리합니다. e1=20분, e2=32분이면 60분보다 64분이 더 느립니다. CPU/RAM 자원 조건만으로 속도 개선을 보장할 수 없습니다.

재현 검산: node report/check-experiment-plan.mjs. 원격 작업 없이 시간표와 단일 생성/실행 슬롯의 닫힌 식을 대조합니다.

E0와 E1: 무엇을 고정하고 언제 멈출까?

E0 자원 보정: 공개된 동일 검사 작업 3개를 사전 고정합니다. 후보 생성은 하지 않으며 보호 최종 검사 자료도 사용하지 않습니다. 같은 작업당 CPU/RAM 제한·명령·고정 초기 cache에서 슬롯 1개와 2개를 각각 실행합니다. 조건 순서는 1→2와 2→1로 두 쌍을 기록하되 이는 성능 우위의 통계 검정이 아닙니다. 처리 경과시간·작업별 시간·최대 RSS·I/O·무효를 남깁니다. 슬롯 2개에서 안전 조건을 만족하지 못하면 E1은 슬롯 1개로 진행할 수 있습니다. 판정이 흔들리면 환경을 먼저 수정합니다.

전체 VM을 혼자 쓰는 검사와 둘이 자원을 나눠 쓰는 비교는 별도의 운영 정책 실험입니다. E0의 같은 작업당 제한 비교와 합치지 않습니다. Cargo의 --jobs와 테스트 스레드는 각각 제한하고, cache 쓰기 영역과 프로세스를 격리합니다. 검사 동시 실행 수와 모델 동시 작업 수는 별개입니다.

E1 본 파일럿: 과제 1개를 A/B 독립 세션에 한 번씩 배정합니다. 실행 순서와 리뷰 제시 순서를 기록하고, A/B는 같은 VM에서 동시에 실행하지 않습니다. 사용자가 지정한 gpt-6-astra 구독 경로를 사용하며 실제 모델 ID·effort·버전·도구·공개 자료·총예산·슬롯을 같게 고정합니다. 초기 LLM 작업은 한 개이며 다중 후보와 의무 ToC 검토는 포함하지 않습니다. A의 자율 계획과 공개 검사는 허용합니다. B의 준비·구조화 비용은 B에 포함합니다.

공개 검사 후 재제출은 최대 1회입니다. 최종 후보 revision을 고정한 뒤 보호 검사는 1회 시행합니다. 보호 입력·정답·개별 로그는 후보 세션에 반환하지 않습니다. 최종 실패를 고치려면 해당 실험을 종료하고 새 변경으로 진행하며, 노출한 자료는 이후 독립 확인 자료로 사용하지 않습니다.

인프라 장애의 동일 revision 재실행도 최대 1회이며 같은 총 시간 예산을 사용합니다. 실행 전 남은 프로세스·파일·cache를 확인합니다. 후보가 자원 한도를 넘긴 경우에는 그 비용을 결과에 남기며, 외부 장애처럼 제외하지 않습니다. 원인이 불명확하면 미확정으로 남깁니다. timeout은 미완료, 0 tests·증거 누락은 무효, 출력 반례는 결함으로 구분합니다.

실행 잠금: VM 비용 상한, 작업당 CPU/RAM/디스크/출력 상한, smoke·trial timeout, 모델 사용량 상한과 중단 수단, 검토자를 기록·승인하기 전에는 실행하지 않습니다. 관측할 수 없는 토큰 사용량을 0으로 채우지 않습니다. 예비 smoke에도 별도의 시간·자원·비용 상한을 먼저 승인합니다. 그 측정 뒤 본 실험의 운영 값을 고정하고 A/B 중간에는 바꾸지 않습니다.

측정된 실패도 다시 확인하는 판정 기준

오류 주입 구현은 먼저 컴파일·실행 가능하며 독립 기대값과 실제로 다른 출력을 내는지 확인합니다. 동등한 결과를 내는 무효 변이는 이유를 남기고 분리합니다. 생성된 검사는 정상 구현에서 통과하고 오류 구현에서 의도한 출력 assertion으로 실패할 때 검출로 셉니다. compile error, OOM, 0 tests, runner 오류는 오류 검출 성공이 아닙니다.

실제 구현검사 통과의도한 assertion 실패
정상TN · 정상 통과FP · 정상 오탐
오류 주입FN · 오류 누락TP · 오류 검출

양성은 ‘오류가 있다고 판정’입니다. 무효·미완료·미실행은 표 밖에 따로 집계합니다. 이 작은 통제 집합의 결과를 컴파일러 전체 오류 확률로 확대하지 않습니다. 보호 기준이나 실행기를 고치면 영향을 받은 A/B 양쪽을 무효화하고 새 기준에서 재평가합니다.

배정된 모든 과제에 완료 여부와 누적 사람 작업시간을 함께 보고합니다. 실패한 과제를 제외한 평균만 사용하지 않습니다. 사람 작업시간은 준비·개입·정리·리뷰·직접 수정의 시작/끝과 역할/이유로 기록하며, 공통 환경 준비 비용은 별도로 보여 줍니다.

Stanford planning과 Tree-of-Concerns를 적용한 범위

SPRINT의 독립 작업 분해와 결과 수집을 의존성 기반 실행에 참고했습니다. Running Context 동기화는 독립 평가가 아닙니다. LATS의 대안 탐색을 쓰려면 파일뿐 아니라 프로세스와 부수효과의 복원 조건이 필요합니다. 학습된 SPRINT나 MCTS를 구현하는 것이 이번 실험의 선행 조건은 아닙니다.

E2에서 필요가 확인되면 의미·판정기·재현성 세 관점으로 쟁점을 나눕니다. 각 지적은 코드 위치·위반 조건·반례 또는 검사 명령을 포함하고, 반박 근거가 있으면 철회합니다. 잔여 지적을 실행 검사의 입력으로 사용하며 모델 합의로 통과시키지 않습니다. ToC 원문의 논문 비평 효과를 컴파일러 검증 효과로 간주하지 않습니다.

E2는 한 번에 한 질문만 추가합니다. 먼저 동일 총 모델 예산에서 단일 후보와 최대 3개 후보의 차이를 보거나, 고정된 후보에 단일 검토와 세 관점 검토를 비교합니다. 두 변경을 동시에 추가하지 않습니다. 폭·수정·검토 상한과 중단 규칙을 사전 고정하며 이미 있는 Git·Codex 기록을 재사용합니다.

Nebius 제품 경로와 실제 실행 자원의 경계

기본 검토 경로는 AI Cloud의 x86-64 CPU VM이며 현재 자원 예산은 8 vCPU·32 GiB입니다. 실제 할당이나 계정 이용권을 확인한 상태는 아닙니다. Token Factory Sandbox는 베타 접근·실제 아키텍처·CPU/RAM·쓰기 공간을 확인한 뒤 선택할 대안입니다. 두 환경의 수치를 혼합하지 않습니다.

Token Factory 이용권을 AI Cloud VM 임대권이나 비용 상한으로 간주하지 않습니다. Sandbox 쓰기 layer schema의 기본값도 VM RAM/디스크 사양이 아닙니다. 실제 자원·접근·과금 조건은 실행 전에 별도로 확인합니다. 개인 계정 조회 기록은 공개하지 않습니다.

비교를 시작하기 전에 고정할 운영 조건
  • 재제출·재실행 상한과 E0/E1 반복 단위는 위 계약을 따릅니다. 시간·사용량·자원 상한과 검토자 값은 예비 확인 후 고정하며, 미입력 상태는 실행 중단 조건입니다.
  • 공통 환경 구축 비용은 별도로 기록합니다. B 전용 계약 작성, 재현 준비, 정리 비용과 양쪽의 사람 개입·검토·재작업은 해당 조건의 비용에 포함합니다.
  • 제시 순서를 섞어도 같은 사람이 같은 문제를 두 번 검토하면 학습 효과가 남습니다. 첫 파일럿에서는 이를 기록하고, 효과 비교로 확장할 때 과제·순서·검토자 배치를 다시 설계합니다.
  • 실행 실패나 검사 로그 누락은 코드 결함과 구분합니다. 제한 시간 도달은 미완료입니다. 확인된 반례는 수정 또는 기각으로, 불충분한 증거는 보류로 보냅니다.
  • 기존 Codex 기록, Git diff, stdout/stderr, 검사 결과를 연결합니다. 요약·해시만 남기지 않고 판정에서 실제 값과 원문으로 이동할 수 있게 합니다. 새 DB·trajectory 규격·자동 절차 변경 시스템은 만들지 않습니다.
