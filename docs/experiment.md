# 실험 계약: 자원 효과와 작업 절차 효과를 분리한다

상태: **2026-09-14 AWS 무변경 Rust CPU smoke·수거·자원 삭제 완료.** 모델 A/B·검사 병렬도 비교·NPU·Nebius CI는 미실행입니다. 이 문서는 실제 준비 검사와 후속 계획을 구분합니다. [시행도](../report/assets/compiler-ax-experiment-approval.html#execution)는 후속 설계의 준비·권한·검사 후 조치와 회수 조건을 요약합니다. 공통 검사 기준은 [품질 계약](quality.md), 첫 과제의 입력·수치·데이터 이동은 [커널 계약](kernels/double-buffering.md)에 둡니다.

후속 공개 단일 변경으로 double-buffering 테스트·독립 oracle·오류 주입 patch를 작성했습니다. 2026-09-15 KST 로컬 Docker amd64/Rosetta에서 정상 SDK 3개·18 case·46,080개 값 비교와 helper 2개가 통과했고, 별도 오류 checkout은 컴파일 후 예상한 수치 assertion으로 실패했습니다. fmt·표적 Clippy도 통과했습니다. 이 작업은 아래 A/B 실험의 어느 arm에도 배정하지 않습니다. 공개 입력과 이미 본 오류 patch는 보호 최종 평가로 재사용하지 않습니다. [실행 조건과 원문 판정](kernels/double-buffering.md#8-로컬-docker-실행-결과)

구현 파일과 상세 스펙은 [architecture 인덱스](architecture/00-OVERVIEW.md)에서 읽습니다. [원격 명세](architecture/02-REMOTE-EXECUTION.md)는 아래 실험 방법을 바꾸지 않고, 실행 주체·데이터 접근·필드·실패와 회수 절차를 구체화합니다.

## 시행 보류와 재개 조건

**2026-09-14 후속 사용자 지시로 로컬 구현·회귀 검사를 재개합니다.** 앞선 설계 정렬만 수행하던 보류를 해제하고 실행기 보완부터 진행합니다. 원격 smoke·클라우드 자원 생성·모델 비교는 아래 비용·접근·환경·판정 조건이 확정된 범위에서 별도로 진행합니다. 문서·데모 회귀 결과를 Rust 실험 결과로 계산하지 않습니다. 이 문서는 무제한 실행 허가가 아닙니다.

1. 사용자의 명시적 재개 지시를 확인합니다. 이번 로컬 구현 재개는 확인됐으며, 로그인·계정 변경만으로 추가 실행 범위를 넓히지 않습니다. 개인 계정 사정은 공개 문서에 남기지 않습니다.
2. 재개 환경에서 실제 model ID·effort·이용 가능 범위·사용량 관측 수단을 다시 확인합니다. 이전 세션의 한도·권한·설정을 승계하지 않으며, A/B에는 같은 공개 조건과 실행 한도를 적용합니다. 비교 중 계정·모델·사용 한도처럼 비교에 영향을 주는 조건이 바뀌면 중단하고, 변경 전후 결과를 같은 비교로 합치지 않습니다.
3. 실행할 단계의 조건을 확정합니다. 무변경 `binary_add` smoke에는 host·toolchain/native artifact·기존 명령·기대 실행 수·담당자·시간/비용·회수 조건이 필요합니다. double-buffering 검사에는 [입력·수치 계약](kernels/double-buffering.md)과 대조군을 추가로 확정합니다. 검사 병렬도 보정·A/B 비교 전에는 공개 검사 세 개, [판정 단위](#결함-검출의-판정-단위), 보호 평가·접근 검증, 모델 조건과 모든 상한을 확정합니다. 후속 단계의 준비를 smoke의 선행 조건으로 소급하지 않습니다.
4. 실행기 보완과 Rust 연결 상태를 확인한 뒤, 허가된 범위의 무변경 CPU smoke부터 시작합니다. smoke와 비교 실험의 승인은 구분합니다.

## 구현하는 목적과 완성 조건

에이전트가 만든 테스트가 정상 동작과 알려진 오류를 구별하는지 확인하고, 그 변경을 사람이 검토하는 데 든 작업시간과 재작업을 비교할 수 있는 최소 실행 환경을 만듭니다. 첫 산출물은 공개 Rust 예제에 추가한 회귀 테스트, 실제 검사 기록, 사람이 채택·반려할 수 있는 작은 diff입니다. 생성 코드량·테스트 개수·초록색 CI만으로 유용성을 판단하지 않습니다.

구현의 대상은 고정된 x86 빌드 환경, 기존 명령을 호출하는 Rust 검사 연결, 결과·실제 테스트 수·중단 사유 기록, 승인된 원격 실행과 자원 회수입니다. 후보 생성에는 기존 Codex 구독 세션을 사용하고 CI는 고정된 후보를 검사합니다. 새 agent framework, KG 엔진, 상시 runner, 모델 학습 또는 NPU 최적화기를 선행 구축하지 않습니다. [지식 구조 선택의 근거](context.md)

구현 완료는 변경 없는 baseline과 실패 대조군을 실행할 수 있고, 0 tests·불완전 결과·timeout을 성공으로 처리하지 않으며, 취소 뒤 자원이 남았는지 확인할 수 있는 상태입니다. 실험 완료는 검사 병렬도 보정과 에이전트 작업 절차 비교의 결과, 독립 최종 검사 판정, 사람의 채택 검토 결정 및 정리 기록이 남은 상태입니다. 실패나 효과 없음도 완료된 실험 결과가 될 수 있지만, 보호 검사를 수행하지 못하면 에이전트 작업 절차 비교는 미완료로 기록합니다. 실제 PR 병합·upstream 제출·릴리스는 별도 승인입니다.

## 작업과 환경

2026-09-14 후속 승인에 따라 첫 무변경 CPU smoke를 AWS 서울의 `m7i.large` 1대(2 vCPU·8 GiB), 암호화된 20 GiB gp3에서 완료했습니다. 승인 상한은 최대 2시간·예산 1 USD였으며, Ubuntu 24.04 x86-64의 고정 AMI와 build jobs=1을 사용했습니다. [관측성·기록 규약](quality.md#cpu-smoke의-관측성과-기록-규격)에 따라 수거 뒤 새 instance·disk·보안그룹·키페어의 종료/삭제를 재조회했고 기존 서버는 유지했습니다. 계정·AMI·자원 ID와 API 원문은 비공개 실행 기록에 있습니다.

[Token Factory Sandboxes beta](token-factory-sandbox.md)는 신청 접수 후 실행 권한 승인을 기다립니다. 아래 Nebius AI Cloud·컨테이너·main CI는 후속 설계로 남깁니다. 이번에는 운영자의 로컬 AWS CLI/SSH와 일회성 VM에서 변경 없는 공개 코드를 검사하며, 후보 격리·본 비교·상시 CI의 검증으로 해석하지 않습니다. 본 실험의 과제·판정·보호 평가 조건은 바꾸지 않습니다.

고정 대상은 `furiosa-opt` 0.8.1, commit `9b9cf0fdc78df00cdc430eae725a5ad9084a735e`, Rust `nightly-2026-05-01`입니다. 첫 과제는 double-buffering의 세 구현에서 그룹별 출력·경계를 확인하는 테스트 보강입니다. 실제 제품 결함을 발견한 상태는 아닙니다.

[커널 문서](kernels/double-buffering.md)는 운영자의 준비·조사 경로도 담습니다. 후보에게는 이 문서 전체가 아니라 입력·의미·허용 파일·공개 검사 요구를 추출해 같은 판본으로 제공합니다. 세 구현의 본체·mapping·schedule 또는 독립 판정 기준을 수정해야 한다면 첫 과제의 조건이 바뀌므로 작업을 멈추고 범위를 다시 확정합니다. 이 분기와 공통 계약이 B에만 유리한 정보 차이가 되지 않도록 A/B 공개 입력 목록을 함께 고정합니다.

초기 후보는 Nebius AI Cloud의 `cpu-d3`, `8vcpu-32gb` x86-64 VM 한 대로, 8 vCPU·32 GiB RAM 구성입니다. 이는 실제 할당이나 공급사 최소 요구, 충분성을 입증한 측정값이 아닌 계획입니다. 고정 upstream Dockerfile에 맞춰 Ubuntu 24.04 host와 digest를 고정한 Ubuntu 24.04 amd64 빌드 컨테이너를 선택합니다. 이전 22.04 컨테이너안은 최소 지원 OS를 필수 OS로 고정할 이유가 없어 대체합니다. 컨테이너는 host kernel을 공유하며, Dockerfile만으로 배포 binary와 native library가 준비되지는 않습니다. 해당 artifact의 출처·버전·hash와 `x86_64-unknown-linux-gnu`·GLIBC 2.34 이상·고정 nightly의 실제 호환성을 smoke에서 확인합니다. 지역·image ID/digest·디스크 종류와 크기·작업별 자원은 승인 전에 확정합니다. Token Factory 이용권을 AI Cloud VM 이용권으로 가정하지 않습니다. [공식 자료](sources.md)

고정 예제의 입력·출력 원자료는 논리적으로 27 KiB입니다. 중간 버퍼·복사·oracle·Rust 빌드 RSS는 포함하지 않습니다. 32 GiB는 텐서 크기에서 도출한 요구량이 아니며, 빌드와 검사 병렬도의 실제 최대 RSS·I/O를 확인할 선정안입니다. 정확한 축·dtype와 계산 범위는 [입력·수치 계약](quality.md#입력과-수치-계약)에 둡니다.

키·결제·계정 상태는 공개 문서에 기록하지 않습니다. 실행 전 비용 상한, smoke/trial timeout, 작업별 CPU·RAM·디스크·출력 상한, 모델 사용량 상한과 중단 수단, 검사 담당자를 확정합니다. 준비 명령에도 한도가 필요합니다. 미확정이면 실행을 시작하지 않습니다.

## 처음부터 종료까지의 순서

아래는 시행 절차이며 실행 완료 기록이 아닙니다. 명령·입력·시간 및 비용 한도·정상과 오류 대조군 목록을 채운 실행 계약을 별도로 승인받기 전에는 유료 작업을 시작하지 않습니다. 검사 병렬도 보정에 쓸 공개 검사 세 개도 정확한 이름과 명령을 준비 단계에서 고정하며 임의로 채우지 않습니다.

| 단계 | 수행과 산출물 | 다음 단계로 갈 조건 |
|---|---|---|
| 0. 범위 확정 | 테스트할 동작, 허용 Rust 파일, source/toolchain pin, 동일 A/B 공개 요구, 검사 목록·담당자·예산을 고정합니다. | 누락된 접근·자원·판정 조건이 없습니다. |
| 1. 실행 환경 준비 | 변경 없는 upstream checkout을 빌드하고 기존 `test_binary_add_2048`를 실행합니다. VM·컨테이너·native artifact·실제 명령을 기록합니다. | 지정 테스트가 실제 실행되고 결과가 독립 기대값과 일치합니다. |
| 2. 검사기·운영 검증 | 정상/의도 오류 대조군, 0 tests·형식 오류·timeout을 구별합니다. 취소와 잔존 VM·디스크 회수도 시험합니다. | 오류를 assertion으로 검출하고, 실행 불능을 결함 검출로 세지 않습니다. 보호 평가의 접근 경계도 준비돼야 에이전트 작업 절차 비교를 시작합니다. |
| 3. 검사 병렬도 보정 | 동일 공개 검사 묶음을 슬롯 1/2에서 비교합니다. 경과시간·최대 RSS·I/O·cache·무효 결과를 남깁니다. | 자원 한도와 유효성을 지키는 실행 설정을 선택합니다. |
| 4. 에이전트 작업 절차 비교 | A/B의 독립 Codex 세션이 같은 테스트 보강 과제를 수행합니다. B만 추가 절차 안내를 받습니다. 공개 검사와 허용된 재제출 뒤 snapshot을 고정합니다. | 각 후보의 diff·공개 검사·작업시간·미완료 사유가 남습니다. 예산 종료도 결과입니다. |
| 5. 독립 최종 검사 | 고정 후보의 테스트를 보호된 정상/오류 구현에 적용합니다. 검사기·기대값·판정은 후보 밖에서 관리합니다. | TP/FP/TN/FN과 무효·미완료를 분리하고 개별 보호 증거를 repair에 돌려주지 않습니다. |
| 6. 사람의 채택 검토·정리 | 후보별 정확성·범위·검토 부담을 보고 채택/반려/보류합니다. 결과를 보존한 뒤 실험 자원을 삭제하고 잔존 여부를 확인합니다. | 배정된 모든 후보의 종료 이유와 자원 회수 결과가 기록됩니다. 병합 여부와 별개로 실험 결론을 남깁니다. |

## Nebius CI의 책임과 구현 순서

기존 GitHub-hosted PR CI는 그대로 유지합니다. 신뢰된 `main`의 별도 수동 workflow만 소유자 승인 뒤 Nebius VM을 생성·수거하도록 구현합니다. dispatch의 branch 선택도 검증하고 secret이 있는 environment는 정확히 `main` branch만 허용합니다. 소유자 승인은 독립 동료 리뷰가 아닙니다.

- **controller:** 전용 service account의 authorized key를 secret으로 관리하고 프로젝트 범위 권한을 제한합니다. 공식적으로 확인된 CLI 인증 경로이며, GitHub에서 Nebius로 들어가는 OIDC 연동이 구현돼 있다고 가정하지 않습니다. workflow와 action revision, PR head/base/실제 test-merge SHA를 기록합니다.
- **worker:** GitHub runner를 설치하지 않고 원격 검사만 실행합니다. Nebius 관리 키, GitHub write token, 개인 Codex 인증정보, SSH agent forwarding을 제공하지 않습니다. 후보는 비특권 컨테이너에서 실행하며 host socket·보호 자료를 mount하지 않습니다. dependency 준비 뒤 후보 실행의 네트워크와 metadata 접근을 제한합니다. 권한 격리의 실제 작동을 점검해야 하며 MD나 hash로 대신하지 않습니다.
- **결과:** stdout/stderr는 크기를 제한한 파일로 수집하고 원격 산출물을 controller에서 실행하지 않습니다. 신뢰된 판정기가 형식·실제 테스트 수·exit code·revision을 확인해 안전한 요약을 만듭니다. 처음에는 CPU receipt를 소유자가 PR에서 확인합니다. `main` dispatch 성공이 자동으로 PR required check가 되는 것은 아닙니다. 자동 연결은 PR revision 재확인과 stale 결과 거부를 검증한 뒤 추가합니다.
- **회수:** run ID·소유 범위·만료시각과 정확한 VM/디스크 식별자를 기록합니다. 종료·실패·취소 뒤 삭제하고 별도 정리 작업으로 만료된 이 실험의 잔존 자원만 확인합니다. VM-managed 디스크를 우선하며 별도 IP·disk를 만들면 해당 자원도 추적합니다. 실행용 임시 키·인증 파일도 회수하되 운영용 service account를 임의로 삭제하지 않습니다. API 삭제 요청의 반환만으로 회수 완료를 기록하지 않습니다. 재조회할 수 없으면 `회수 미확인`으로 남기고 운영자가 확인할 때까지 새 실행을 보류합니다. 예산 알림은 자동 지출 차단이 아니며, 저장장치 비용 때문에 VM stop만으로 종료하지 않습니다.

구현은 **Rust 검사 연결 코드의 로컬 회귀 → 승인된 무변경 원격 smoke 및 취소·회수 검사 → 공개 PR 검사 연결 → 보호 평가 환경 준비·접근 검사 → 검사 병렬도 보정 → 에이전트 작업 절차 비교** 순서로 검증합니다. 실제 Rust binary 실행은 호환되는 x86 환경에서만 수행합니다. 보호 평가 환경을 먼저 준비하는 것과 후보의 독립 최종 검사 점수를 미리 측정하는 것은 다릅니다. 후보별 독립 최종 검사는 에이전트 작업 절차 비교의 공개 작업이 모두 끝난 뒤에만 수행합니다. 초기 동시 VM 수는 한 대이며, 검사 병렬도 보정의 슬롯 수는 한 VM 내부 검사 병렬도입니다. 에이전트 작업 절차 비교의 A/B를 동시에 돌리는 의미가 아닙니다. [인증·이미지·삭제의 원문](sources.md)

승인은 계약·환경 확인을 위한 smoke와 본 실험인 검사 병렬도 보정·에이전트 작업 절차 비교로 구분합니다. smoke 허가만으로 후보 생성·보호 평가·후속 실험을 시작하거나 예산을 늘리지 않습니다.

## 준비: 코드보다 실행기와 판정기를 먼저 확인한다

고정 checkout·toolchain·native artifact를 준비하고 변경 없는 `test_binary_add_2048`를 실행합니다. 실제 테스트 수와 assertion을 확인합니다. 배포 binary를 사용하는 공개 경로이며 비공개 compiler 전체를 source build하는 것이 아닙니다.

여기서 **환경 기준 실행의 통과**는 빌드·검사 경로가 준비됐다는 뜻입니다. **정상 구현 대조군**은 생성 테스트의 오탐을 확인할 대상이고, **기본 Codex 절차**는 B의 작업비용을 비교할 기준입니다. 세 역할을 하나의 baseline PASS로 합치지 않습니다. 테스트 보강의 완료에는 새 테스트의 정상/오류 구별, 필수 검사와 사람의 채택 검토가 더 필요합니다. 현재 정수 데모의 `PASS → READY_FOR_REVIEW`를 Rust 준비 검사에 그대로 이식하지 않습니다. [미구현 경계](architecture/01-LOCAL-TRIAL.md#실제-rust-과제로-이행하기-전)

독립 기대값과 정상·실행 가능한 오류 대조군을 준비합니다. 초안 작성은 host 준비와 병렬로 할 수 있지만 실제 대조군 검증은 host가 준비된 뒤에 합니다. 오류 주입이 compile error·OOM 대신 의도한 출력 차이를 만드는지 확인합니다.

첫 과제는 제품 구현의 최적화가 아닌 테스트 보강입니다. 후보가 만든 테스트는 정상 구현의 요구 동작을 유지하면서 알려진 출력 오류를 찾아야 합니다. 공개 개발용 오류와 보호 최종 오류는 분리합니다. 보호 대조군마다 어느 요구를 어기는지, 정상 구현과 어떻게 다른지, 기준 검사로 어떻게 확인했는지를 평가 준비 담당자가 기록합니다. 근거가 불명확한 변이를 점수 분모에 넣지 않습니다. 독립 최종 검사에서 정상 통과와 오류 검출은 채택의 필요조건이며, 테스트의 가독성·범위·유지비 검토까지 대신하지 않습니다.

이 문서와 HTML이 공개한 경계 예시는 공개 개발용입니다. 독립 최종 확인에는 노출하지 않은 구체 입력·변이·판정 구현을 별도 권한으로 보관합니다. 이 운영 저장소의 `.gitignore`만으로 후보 접근이 차단되는 것은 아닙니다.

독립 최종 검사는 공개 CI job과 별도 실행 환경에서 수행합니다. 후보 세션과 생성된 테스트 코드의 파일·네트워크 접근을 제한해 보호 fixture 저장소·정답 파일·구현의 정상/오류 label·최종 판정기·다른 후보 결과를 노출하지 않습니다. 신뢰된 실행기가 필요한 입력 값만 고정 인터페이스로 테스트에 공급합니다. 실행 중 테스트가 처리하는 값까지 보이지 않는다고 가정하지 않으며, 구체적인 공급·검사 방식은 구현 전에 확정합니다. 개별 입력·로그·판정은 후보 생성 세션의 수정에 반환하지 않습니다. 공개 artifact에는 집계 판정과 snapshot 식별자만 남깁니다. 이 경계를 실제로 확인하지 못하면 공개 CPU smoke까지만 수행하고 에이전트 작업 절차 비교의 시작을 보류합니다.

## 검사 병렬도 보정

생성 없이 공개 검사 3개를 고정해 슬롯 1/2에서 재실행합니다. 작업별 CPU·RAM·명령·초기 cache를 같게 하고 1→2, 2→1 두 쌍을 기록합니다. Cargo jobs, libtest threads, 내부 thread pool, 쓰기 cache 경로를 따로 제한합니다.

경과시간·최대 RSS·I/O·무효 결과로 설정을 고릅니다. 안전 조건이 깨지면 중단하고, 2슬롯이 느리면 1슬롯을 선택합니다. VM 전체를 한 작업이 쓰는 조건과 둘이 나누는 조건의 비교는 다른 운영 정책 실험입니다.

`T1=3e1`, `T2=2e2+h`인 검사 전용 예시에서 `2e2+h < 3e1`일 때만 이 조건의 병렬화가 유리합니다. e1=20분, e2=32분이면 60분보다 64분이 느립니다. [산술 검사](../report/check-experiment-plan.mjs)는 계산 예시일 뿐 측정 결과가 아닙니다.

## 에이전트 작업 절차 비교

유지보수 과제 1개를 기본 Codex 절차(A)와 근거 기록 절차(B)의 독립 세션에 각 1회 배정합니다. A는 평소 Codex 작업을 수행하고, B는 보존할 동작·허용 수정·검사 근거를 먼저 기록하는 절차를 받습니다. A도 자율 계획·재현·추가 검사를 할 수 있습니다. 모델·effort·도구·공개 요구·품질 문턱·자원·총예산은 같습니다.

모델은 계획된 Codex 구독 경로이며 실제 model ID·effort·version·사용량 관측 수단은 시작 전에 기록합니다. 구독을 무제한 사용권으로 가정하지 않습니다. 관측 불가능한 사용량을 0으로 채우지 않습니다.

실행·리뷰 제시 순서를 섞어 기록하며 A/B는 같은 VM에서 순차 실행합니다. 같은 검토자의 학습 효과와 자료 형식에서 조건을 추측할 가능성을 한계로 남깁니다. B의 준비·기록 비용도 B에 포함합니다. 초기 LLM 작업은 1개이며 의무 다중 후보·쟁점 검토는 없습니다.

같은 VM을 쓰더라도 후보별로 새로운 checkout·컨테이너·쓰기 cache를 사용합니다. 공유할 수 있는 것은 사전에 고정한 읽기 전용 dependency뿐이며, 앞 후보의 대화·patch·테스트 결과·작업 디렉터리를 다음 후보에게 전달하지 않습니다. model ID와 effort, 공개 컨텍스트·예산은 같게 유지하고 실제로 확인할 수 없는 provider 내부 버전은 고정됐다고 쓰지 않습니다.

범위·코드 품질 검사, 출력 동작 검사, 통합·문서 검사까지의 공개 검사 뒤 재제출은 최대 1회입니다. 확인된 인프라 장애의 동일 revision 재실행도 최대 1회이며 같은 총예산 안에서 진행합니다. 재시도 전에 잔존 파일·프로세스·cache를 확인합니다. 후보 유발 자원 초과는 결과·비용에 포함하고, 원인 미확정은 그대로 기록합니다. 외부 인프라 장애로 재분류해 평가에서 제외하지 않습니다.

A/B 양쪽의 최종 snapshot을 모두 고정한 뒤 후보별 독립 최종 검사를 1회 수행합니다. 한쪽의 보호 결과가 다른 쪽의 생성·수정이나 운영자 안내에 섞이지 않도록 두 조건의 공개 작업을 먼저 끝냅니다. 보호 입력·정답·개별 로그를 같은 후보의 수정에 반환하지 않습니다. 실패 뒤 수정은 새 실험이며 노출 자료를 독립 확인용으로 재사용하지 않습니다. 기준·runner 변경은 영향을 받은 A/B 양쪽 증거를 무효화합니다.

## 결과와 종료

주 지표는 과제별 총 사람 작업시간입니다. 준비·개입·정리·리뷰·직접 수정의 담당자, 시작·끝, 이유를 남깁니다. 공통 환경 준비는 별도 표시합니다. 배정된 모든 과제의 완료·기각·미완료, 경과시간·계산 비용·회귀를 함께 보고합니다. 실패 과제를 제외한 평균만 사용하지 않습니다.

결과 묶음은 요청·후보 revision, 명령·환경·실제 테스트 수, expected/actual·원문 diagnostic, 후보별 상태·시간·비용, 검토자의 결정과 이유로 구성합니다. 기존 Codex 기록은 가능한 범위의 원본 locator를 사용하고, 수집할 수 없는 trajectory나 사용량은 누락으로 표시합니다. 새 event DB나 전체 로그를 대체하는 hash 요약을 만들지 않습니다. 최종 문서는 무엇을 더 빠르게 만들었는지가 아니라 무엇을 올바르게 검토했고 어느 비용이 줄거나 늘었는지 설명합니다.

독립 최종 검사 결과와 사람의 채택 검토를 함께 보고 절차를 유지·수정·폐기합니다. B가 기준을 충족하면서 검토 부담이 줄어들면 다음 과제로 재검증하고, 기록 부담만 늘거나 판정 품질이 떨어지면 절차를 줄이거나 중단합니다. 작은 A/B 한 쌍으로 일반적 효과를 선언하지 않습니다. 수행할 PR이 있으면 [병합 절차](merge.md)대로 현재 head/base를 다시 확인하며, 추가 유료 검사는 남은 예산과 별도 실행 권한 안에서만 합니다.

### 결함 검출의 판정 단위

이번 양성은 **테스트가 결함을 검출한 결과**입니다. 이전 보고서의 **채택 가능한 성능 개선 후보**를 양성으로 둔 선별 판정과 구분하며 두 FP/FN을 합산하지 않습니다.

1. 한 판정 단위는 **고정 후보 테스트 묶음 × 사전등록된 구현 ID**입니다. 구현 ID는 variant와 정상/변이 revision을 식별합니다. 입력 case·출력 위치·assertion은 원인을 찾는 하위 기록이며 각각을 별도 점수로 늘리지 않습니다. 정상·오류 구현 목록과 필수 입력의 공급·실행 방식은 A/B 시작 전에 고정합니다.
2. 정상 구현에서 필수 입력·검사가 모두 실행돼 통과하면 TN, 유효한 출력 assertion으로 실패하면 FP입니다. 오류 구현에서 사전 확인한 요구 위반을 출력 assertion으로 잡으면 TP, 필수 검사가 끝까지 통과해 놓치면 FN입니다. 무관한 assertion 실패는 의도 오류 검출로 세지 않고 원인을 기록해 판정을 보류합니다.
3. 0 tests·실행 누락·필수 증거 손실·compile/runner 오류는 무효, timeout은 미완료로 별도 집계합니다. 오류 assertion 뒤의 정상적인 조기 종료와 실행기 고장을 구분합니다. 부분 관측은 남기되 이를 완전한 정상 통과로 채우지 않습니다.
4. 후보별 사전등록 정상·오류 총수, 판정 가능한 각각의 수, TP/FP/TN/FN, 무효·미완료·보류 수를 함께 보고합니다. 비율을 쓰면 분모와 미판정 수를 함께 밝히고, 하나라도 필수 판정이 남으면 독립 최종 검사 완료로 처리하지 않습니다. 작은 통제 집합의 관측을 컴파일러 전체 오류율로 확대하지 않습니다.

첫 비교는 실현 가능성과 비용 위치를 확인하는 파일럿입니다. 일반 생산성 우위나 NPU 성능을 결론내리지 않습니다. 실험 채택 이후의 lab PR, upstream 제출, 실제 병합·릴리스는 [별도 절차](merge.md)입니다.
