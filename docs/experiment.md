# 실험 계약: 자원 효과와 작업 절차 효과를 분리한다

상태: **설계 완료, CPU·클라우드·모델 실험 미실행**. [시행도](../report/assets/compiler-ax-experiment-approval.html)와 [품질 계약](quality.md)을 함께 읽습니다.

## 작업과 환경

고정 대상은 `furiosa-opt` 0.8.1, commit `9b9cf0fdc78df00cdc430eae725a5ad9084a735e`, Rust `nightly-2026-05-01`입니다. 첫 과제는 double-buffering의 세 구현에서 그룹별 출력·경계를 확인하는 테스트 보강입니다. 실제 제품 결함을 발견한 상태는 아닙니다.

Nebius AI Cloud의 x86-64 CPU VM, Ubuntu 22.04 amd64, 8 vCPU·32 GiB를 검토합니다. 이는 실제 할당이나 공급사 최소 요구가 아닌 초기 계획입니다. 공개 README의 x86_64 Linux·GLIBC·native library 조건을 실제 실행기에서 확인합니다. Token Factory 이용권을 AI Cloud VM 이용권으로 가정하지 않습니다. Sandbox는 접근·아키텍처·RAM·쓰기 공간·실행시간이 충족될 때 별도 대안입니다. [공식 자료](sources.md)

키·결제·계정 상태는 공개 문서에 기록하지 않습니다. 실행 전 비용 상한, smoke/trial timeout, 작업별 CPU·RAM·디스크·출력 상한, 모델 사용량 상한과 중단 수단, 검사 담당자를 확정합니다. 준비 명령에도 한도가 필요합니다. 미확정이면 실행을 시작하지 않습니다.

## 준비: 코드보다 실행기와 판정기를 먼저 확인한다

고정 checkout·toolchain·native artifact를 준비하고 변경 없는 `test_binary_add_2048`를 실행합니다. 실제 테스트 수와 assertion을 확인합니다. 배포 binary를 사용하는 공개 경로이며 비공개 compiler 전체를 source build하는 것이 아닙니다.

독립 기대값과 정상·실행 가능한 오류 대조군을 준비합니다. 초안 작성은 host 준비와 병렬로 할 수 있지만 실제 대조군 검증은 host가 준비된 뒤에 합니다. 오류 주입이 compile error·OOM 대신 의도한 출력 차이를 만드는지 확인합니다.

이 문서와 HTML이 공개한 경계 예시는 공개 개발용입니다. 독립 최종 확인에는 노출하지 않은 구체 입력·변이·판정 구현을 별도 권한으로 보관합니다. 이 운영 저장소의 `.gitignore`만으로 후보 접근이 차단되는 것은 아닙니다.

## E0: 동일 작업의 CPU 슬롯 보정

생성 없이 공개 검사 3개를 고정해 슬롯 1/2에서 재실행합니다. 작업별 CPU·RAM·명령·초기 cache를 같게 하고 1→2, 2→1 두 쌍을 기록합니다. Cargo jobs, libtest threads, 내부 thread pool, 쓰기 cache 경로를 따로 제한합니다.

경과시간·최대 RSS·I/O·무효 결과로 설정을 고릅니다. 안전 조건이 깨지면 중단하고, 2슬롯이 느리면 1슬롯을 선택합니다. VM 전체를 한 작업이 쓰는 조건과 둘이 나누는 조건의 비교는 다른 운영 정책 실험입니다.

`T1=3e1`, `T2=2e2+h`인 검사 전용 예시에서 `2e2+h < 3e1`일 때만 이 조건의 병렬화가 유리합니다. e1=20분, e2=32분이면 60분보다 64분이 느립니다. [산술 검사](../report/check-experiment-plan.mjs)는 계산 예시일 뿐 측정 결과가 아닙니다.

## E1: 같은 과제, 같은 기준, 다른 안내 절차

유지보수 과제 1개를 A/B 독립 세션에 각 1회 배정합니다. A는 평소 Codex 작업, B는 보존할 동작·허용 수정·검사 근거를 먼저 기록하는 절차를 받습니다. A도 자율 계획·재현·추가 검사를 할 수 있습니다. 모델·effort·도구·공개 요구·품질 문턱·자원·총예산은 같습니다.

모델은 계획된 Codex 구독 경로이며 실제 model ID·effort·version·사용량 관측 수단은 시작 전에 기록합니다. 구독을 무제한 사용권으로 가정하지 않습니다. 관측 불가능한 사용량을 0으로 채우지 않습니다.

실행·리뷰 제시 순서를 섞어 기록하며 A/B는 같은 VM에서 순차 실행합니다. 같은 검토자의 학습 효과와 자료 형식에서 조건을 추측할 가능성을 한계로 남깁니다. B의 준비·기록 비용도 B에 포함합니다. 초기 LLM 작업은 1개이며 의무 다중 후보·쟁점 검토는 없습니다.

Q1–Q3 공개 검사 뒤 재제출은 최대 1회입니다. 확인된 인프라 장애의 동일 revision 재실행도 최대 1회이며 같은 총예산 안에서 진행합니다. 재시도 전에 잔존 파일·프로세스·cache를 확인합니다. 후보 유발 자원 초과는 결과·비용에 포함하고, 원인 미확정은 그대로 기록합니다. 외부 인프라 장애로 재분류해 평가에서 제외하지 않습니다.

최종 snapshot 고정 후 Q4 보호 검사는 1회입니다. 보호 입력·정답·개별 로그를 같은 후보의 수정에 반환하지 않습니다. 실패 뒤 수정은 새 실험이며 노출 자료를 독립 확인용으로 재사용하지 않습니다. 기준·runner 변경은 영향을 받은 A/B 양쪽 증거를 무효화합니다.

## 결과와 종료

주 지표는 과제별 총 사람 작업시간입니다. 준비·개입·정리·리뷰·직접 수정의 담당자, 시작·끝, 이유를 남깁니다. 공통 환경 준비는 별도 표시합니다. 배정된 모든 과제의 완료·기각·미완료, 경과시간·계산 비용·회귀를 함께 보고합니다. 실패 과제를 제외한 평균만 사용하지 않습니다.

오류 판정을 양성으로 두면 정상 통과=TN, 정상 assertion 실패=FP, 오류 통과=FN, 오류 assertion 실패=TP입니다. 0 tests·runner 오류는 무효, timeout은 미완료이며 사분면 밖에 둡니다. 작은 통제 집합을 컴파일러 전체 오류율로 확대하지 않습니다.

첫 비교는 실현 가능성과 비용 위치를 확인하는 파일럿입니다. 일반 생산성 우위나 NPU 성능을 결론내리지 않습니다. 실험 채택 이후의 lab PR, upstream 제출, 실제 병합·릴리스는 [별도 절차](merge.md)입니다.

## E2: 필요한 요인 하나만 추가한다

E1 검토 후 같은 총 모델 예산의 단일/최대 3후보 탐색 또는 고정 후보의 단일/세 관점 검토 중 하나를 고릅니다. 두 요인을 한꺼번에 바꾸지 않습니다. 지적에는 코드 위치·위반 조건·반례나 검사 명령이 필요하며 모델 합의로 승인하지 않습니다.
