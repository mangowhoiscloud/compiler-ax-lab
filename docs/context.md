# 판단 컨텍스트

## 목적에서 시작한다

Compiler AX는 코딩 도구를 업무에 연결해 구현·검사·리뷰·문서 유지의 비용을 줄이는 일로 다룹니다. RSI나 RLVR을 먼저 만들기로 결정하지 않습니다. 공개 공고는 역할의 근거이며 실제 조직 병목의 측정값은 아닙니다.

작업이 막히면 행동을 늘리기 전에 관찰 단위를 바꿉니다. 파일별 오류가 반복되면 공통 dependency와 build 조건을, 성공 로그가 실제 결과와 다르면 상태·산출물·판정기의 관계를 봅니다. 높은 추상화 자체가 목표가 아니라 가설을 구별할 관측과 수정 지점을 찾는 것이 목적입니다.

## 보존할 계약을 먼저 고른다

리팩터링은 관련 동작과 인터페이스를 보존합니다. 버그 수정은 결함 동작을 바꾸고 정상 영역을 유지합니다. 기능 추가는 새 요구와 호환성, 수치 최적화는 허용 오차·입력 범위·자원 제약을 합의합니다. 버그가 있는 baseline과 모든 출력이 같아야 한다고 요구하지 않습니다.

ISA는 명령의 아키텍처 계약이고 ABI는 바이너리 경계입니다. IR·vISA·물리 ISA는 같은 표현이 아닙니다. 공개 Furiosa Rust 예제, 배포된 compiler binary, 내부 production compiler 구현도 구분합니다. 소스 이름이나 compile 성공만으로 내부 동작을 추정하지 않습니다.

## 측정 결과와 검사기를 함께 의심한다

정적 검사, host 값 비교, schedule, 물리 장치 측정은 서로 다른 질문에 답합니다. 통과 결과를 읽을 때 실제 테스트가 선택됐는지, assertion이 실행됐는지, 기대값이 대상 구현과 독립인지, revision과 cache가 같은지 확인합니다. 의도 오류 후보와 무변경 대조군으로 검사기의 판정 능력도 시험합니다.

Hash는 원문 bytes의 식별자입니다. 판단에 필요한 입력·단위·실제 값·명령·수정 이유를 hash나 요약으로 대체하지 않습니다. 기존 Codex·Git·CI 기록에서 판정 → 측정값 → 필요한 원문 구간으로 이동하게 합니다. 처음부터 별도 event database를 만들지 않습니다.

## 사례를 시스템에 투사한다

Dioxus에서 가져오는 것은 코드 생성 도구의 이름이 아니라 생성 초안과 병합 가능한 변경 사이의 검사·사람 리뷰입니다. 테스트 조건을 정하고, 발견한 실패를 축소해 회귀 검사로 유지하며, 코드와 문서·예제의 revision을 맞춥니다. coverage 재생과 correctness 검사를 구별합니다. [출처](sources.md)

계획·병렬 실행·결과 동기화는 구분합니다. 먼저 선행 결과와 공유 쓰기 의존성을 확인해 독립 작업만 나란히 배치하고, 완료 결과를 모은 뒤 다음 작업을 정합니다. 대안 행동을 트리로 탐색하려면 같은 출발 상태로 복원할 수 있어야 합니다. 결과 수집이나 탐색 점수는 독립 검증을 대신하지 않습니다. [원문과 적용 범위](sources.md#계획실행검토-원논문의-방법과-이-실험의-선택)

고정 후보의 쟁점별 검토는 필요성이 확인된 뒤 비교할 별도 제안입니다. 첫 에이전트 작업 절차 비교에 학습된 병렬 planner, 트리 탐색기, 다중 에이전트 토론을 의무로 넣지 않습니다. 후보 고정 뒤의 독립 검사와 사람의 채택은 이 실험에서 정한 운영 규칙입니다.

DoRA는 목적·관측 → 기존 설명의 공백 → 분석 관점 → 대응 설계 → 검증·한계라는 서술 전개만 참고합니다. 논문의 수리 설계나 학습 효과를 컴파일러 실험의 근거로 사용하지 않습니다.

## 보고서에서 이번 실험으로 옮긴 범위

이번 실험은 기존 개인 Compiler AX 설계 전체의 재현이 아니라, 그중 작은 유지보수 작업을 검토 가능한 변경으로 마치는 제안을 검증합니다. 기존 설계의 주장과 현재 실행 상태를 다음처럼 대응시킵니다.

| 기존 설계의 질문 | 이번에 옮긴 계약 | 현재 확인 경계 |
|---|---|---|
| 어떤 일을 실제로 개선하는가? | 세 double-buffering 구현의 그룹별 값·경계를 확인하는 테스트 보강 | 과제 선정·source pin만 고정했으며 새 Rust 테스트는 없습니다. |
| 통과한 검사 자체가 틀렸을 수 있는가? | 독립 기대값·정상/오류 대조군·0 tests·무효와 미완료의 구분 | 정수 데모의 판정 검사는 존재하지만 bf16 Rust oracle과 보호 평가는 미구현입니다. |
| 후보가 자신의 합격 기준을 바꿀 수 있는가? | 허용 파일과 보호 reference·오차·parser의 소유권 분리 | MD에 명시했으며 실제 파일·네트워크 접근 차단은 별도 검증이 필요합니다. |
| 어떤 관측 때문에 변경했는지 복원할 수 있는가? | native 기록·diff·명령·결과의 연결과 필수 증거 재검증 | 로컬 데모는 저장 사본·명령·원문 결과를 다시 대조합니다. 원격 trajectory 연결과 설명의 타당성 확인은 별도로 남았습니다. |
| 초안 작성 이후에도 작업 부담이 줄었는가? | 준비·개입·정리·리뷰·수정을 포함한 사람 작업시간과 채택 판단 | 비교 실험은 미실행이며 PR·병합·릴리스도 별도 상태입니다. |

비교 방식은 의도적으로 좁혔습니다. 기존 설계의 기존 업무·단일 후보·병렬 후보 비교를 그대로 실행하지 않고, **기본 Codex 절차와 근거 기록 절차**를 같은 모델·공개 요구·품질 문턱·자원 조건에서 비교합니다. 과제 한 쌍의 파일럿이므로 주 지표는 사람 작업시간이며, 정상/오류 구별과 필수 검사 완료를 전제로 읽습니다. 후보 수와 검토 관점의 효과는 별도 후속 단일 요인 실험으로 남깁니다.

성능 개선 후보의 선별과 생성 테스트의 결함 검출은 서로 다른 판정입니다. 이번 [FP/FN의 양성과 집계 단위](experiment.md#결함-검출의-판정-단위)는 후자에만 적용합니다. 검사 병렬도의 경과시간을 NPU 성능이나 에이전트 절차의 효과로 합치지 않습니다.

추가 구현은 [입력·수치 계약](quality.md#입력과-수치-계약)과 [원격 기록 명세](architecture/02-REMOTE-EXECUTION.md#5-기록의-상세-규격)를 기존 파일에 연결하는 범위입니다. 큰 원문에서 필요한 구간을 찾는 원칙을 적용하되 새 event DB·KG 엔진·범용 실행기를 선행 제작하지 않습니다. 실제 NPU 검사, schedule 최적화와 새 탐색 기법은 첫 유지보수 작업 이후의 선택으로 둡니다.

## 2026-09-14 결정: skill로 실행하고 근거는 링크로 연결한다

**선택:** 기존 skill을 작업 진입점으로 사용하고 `docs/`와 `references/`를 링크형 wiki로 유지합니다. 별도 knowledge graph 추출기·DB·검색 서비스를 이번 구현에 추가하지 않습니다. 관계 구조를 포기하는 결정이 아니라, 관계를 관리할 엔진의 도입을 보류하는 결정입니다.

현재 공개 문서에는 실험·품질 계약과 원문별 채택 이유가 있고, 실행 skill은 `program.md`와 로컬 검사기로 연결됩니다. 반면 상세 컴파일러 지식은 일부 로컬 보존 자료에 있고, 실제 Rust adapter와 Nebius 실행 연결은 없습니다. 먼저 필요한 근거를 공개 가능한 범위에서 연결하고 실제 검사 하나를 끝까지 수행해야 합니다. 검색 엔진은 누락된 근거나 미구현 검사를 대신하지 않습니다.

| 책임 | 정본과 사용 방식 |
|---|---|
| 무엇을 읽을지 | [AGENTS.md](../AGENTS.md)에서 요청에 맞는 문서만 선택합니다. |
| 구조와 스펙을 어디서 확인할지 | [Architecture 인덱스](architecture/00-OVERVIEW.md)에서 현재 로컬 구현과 원격 설계로 나눠 읽습니다. 절차는 번호로 쓰고 필드·생산자·판정 주체를 연결합니다. |
| 무엇을 수행하고 언제 멈출지 | [실행 skill](../.agents/skills/run-bounded-change-loop/SKILL.md)과 [program.md](../program.md)가 안내합니다. 현재 실행 범위는 로컬 데모입니다. |
| 저장소 변경과 PR을 어떻게 인계할지 | [운영 skill](../.agents/skills/review-to-verified-pr/SKILL.md)이 조사·변경·승인된 원격 반영을 나눕니다. 조사 절차는 필요할 때만 읽고 기존 검사·병합 규약을 재사용합니다. |
| 왜 그 규칙을 택했는지 | [출처 대장](sources.md)과 [원문 구조](../references/source-layouts.md)에 원문 위치·판본·채택 이유·적용 범위를 남깁니다. |
| 어떤 결과였는지 | [실행기](../scripts/trial.py)와 실제 검사 기록으로 확인합니다. MD나 source hash를 판정값으로 사용하지 않습니다. |

필요한 연결은 `원문 절 → 채택한 판단 → 로컬 규칙 → 검사 또는 미구현 상태`입니다. 동일 단어의 동시 출현을 검증 관계로 바꾸지 않으며, 자동 추출한 관계도 원문·revision으로 확인해야 합니다. 기존 출처 대장에 적용 위치를 보강하고, 다른 파일에 같은 설명을 복제하지 않습니다. 원문 전사·책·개인 기록이나 운영자 컨텍스트 전체를 공개 repo 또는 A/B 후보에 복사하지 않습니다.

**보류 이유:** 현재는 작업별 읽기 경로가 명확하며, 별도 엔진의 이득을 비교 측정하지 않았습니다. 따라서 "KG는 효과가 없다"는 검증 결과가 아닙니다. 엔진을 도입하면 관계의 의미 검토와 revision 갱신도 운영해야 하므로, 먼저 기존 검색·링크를 기준선으로 둡니다.

**재검토 조건:** "checker 변경으로 어떤 실험 결과를 다시 확인해야 하는가", "host 통과가 잘못 인용된 NPU 주장은 어디인가", "이 설계 근거가 바뀌면 어떤 규칙·검사가 영향을 받는가" 같은 여러 단계의 조회가 반복될 때 비교합니다. 담당자가 확인한 정답 관계를 기준으로 근거 누락·잘못된 연결·검색 시간·갱신 비용을 기록합니다. 기존 링크 검색보다 근거 품질을 유지하며 총 작업 부담을 줄일 때만 엔진을 도입합니다. 이 비교를 첫 에이전트 작업 절차 비교의 필수 과제로 추가하지 않습니다.

## 현재 문서가 과거 기록보다 우선한다

현재 정본은 [검사 병렬도 보정·에이전트 작업 절차 비교 계획](experiment.md)과 [품질 검사·채택 절차](quality.md)입니다. 과거 CI triage 전용 사양은 역사 자료이며 첫 과제나 역할 범위를 제한하지 않습니다. 본 실험은 CPU 테스트 유지보수의 실현 가능성을 확인한 뒤 diff·검사·사람 결정으로 닫습니다. 장치 실험·새 탐색 기법은 이후 별도 질문으로 둡니다.
